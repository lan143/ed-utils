ТЗ: переработка сетевого логгера ESP32 (EDUtils::NetworkLogger)
Версия 1.0 · 05.11.2026 · Исполнитель: агент-разработчик · Платформа: ESP32, Arduino-ESP32 поверх ESP-IDF
1. Цель
Заменить текущую реализацию NetworkLogger так, чтобы логи контроллеров доставлялись на приёмник (далее в Loki) без потерь в штатном режиме, а при перегрузке или недоступности сети потери были ограниченными, явными и посчитанными. Логгер не должен блокировать прикладной код, не должен аллоцировать память в обработчике логов и не должен расти по памяти.
2. Контекст
• Входные файлы: log_config.h, log.h, log.cpp, log_handlers.hpp.
• Логи перехватываются через esp_log_set_vprintf, копятся и уходят HTTP POST (text/plain) на промежуточный приёмник, который сам формирует записи для Loki. Приёмник не меняется (допускается только игнорирование новых заголовков).
• Часть контроллеров работает по Ethernet (в том числе KC868-A2), часть по Wi-Fi. Проверка готовности сети не должна быть привязана только к WiFi.
• Цель отправки меняется в рантайме через LogSettingsHandler.

4. Обязательные ограничения совместимости
• Публичный API сохраняется: NetworkLogger::init(LogConfig, std::string, std::string), setConfig, getConfig, enable, isEnabled, extern EDUtils::NetworkLogger networkLogger, макросы LOGE/LOGW/LOGI/LOGD/LOGV, LogConfig, LogSettingsHandler с onApplied.
• update() остаётся как deprecated no-op: существующие вызовы из loop() должны собираться и ничего не делать.
• addLogRecord(const char*) остаётся как обёртка над записью в ring buffer.
• HTTP-запрос обратно совместим: метод POST, Content-Type: text/plain, заголовки X-SYSTEM и X-INSTANCE. Новые заголовки только добавляются.
• Контракт /api/log/settings (статусы, тексты ошибок, формат JSON) не меняется, кроме явно указанного в §8.
• Не менять версии библиотек и стандарт C++ без согласования. Код должен собираться в текущем окружении проекта (без исключений и RTTI, как в Arduino-ESP32, без фич новее C++11, если проект не собирается новее).
5. Архитектура
5.1 Компоненты
1. Хук vprintf. Выполняется в контексте любой задачи, вызвавшей esp_log_write. Форматирует строку в буфер на стеке, передаёт её прежнему хуку (UART/USB), нормализует копию и кладёт в ring buffer. Только неблокирующие операции.
2. Ring buffer. xRingbuffer типа RINGBUF_TYPE_NOSPLIT, создаётся один раз в init(), размер фиксирован. Потокобезопасен для нескольких писателей.
3. Sender task. Отдельная FreeRTOS-задача низкого приоритета: забирает записи из ring, собирает пачку в заранее выделенный chunk-буфер, отправляет HTTP POST с ретраями и backoff.
4. Конфигурация и состояние. Конфиг, system и instance защищены mutex. Mutex никогда не берётся в хуке.
5.2 Хук
Порядок действий:
1. vsnprintf в локальный буфер размером LOG_NET_LINE_MAX (по умолчанию 256) через va_copy. Оригинальные args не потреблять.
2. Вызвать прежний хук, сохранённый из esp_log_set_vprintf, и вернуть его результат. Если прежнего хука не было, вернуть длину строки.
3. Не слать в сеть, если: сетевой логгер выключен (atomic-флаг), вызов из ISR (xPortInIsrContext()), планировщик не запущен, текущая задача является sender-задачей (защита от петли обратной связи), len <= 0, уровень строки ниже LOG_NET_MIN_LEVEL.
4. Нормализовать копию: убрать ANSI-последовательности ESC[...m (при LOG_NET_STRIP_ANSI), заменить завершающие CRLF на LF, гарантировать завершающий LF. Для усечённой строки добавить маркер усечения и LF.
5. xRingbufferSend с timeout 0. При неудаче увеличить atomic-счётчик dropped. Никогда не блокироваться.
6. Если свободного места в ring меньше порога LOG_NET_FLUSH_THRESHOLD или уровень записи ERROR, разбудить sender через xTaskNotifyGive, но не чаще раза в LOG_NET_URGENT_MIN_GAP_MS.
В хуке запрещены: malloc/new, std::string, mutex, LOGx и printf (рекурсия), любые блокирующие вызовы.
Хук работает на стеке вызвавшей задачи. В стресс-тесте нужно измерить uxTaskGetStackHighWaterMark на самых маленьких прикладных задачах и зафиксировать дополнительный расход стека (цель: не более 1.5 КБ сверх штатного).
5.3 Ring buffer
• Размер LOG_NET_RING_SIZE (по умолчанию 24 КБ), выделяется один раз, не растёт и не пересоздаётся.
• Политика переполнения: отбрасывается новая запись, dropped увеличивается.
• Максимальный размер элемента не больше LOG_NET_LINE_MAX.
• Повторный init() не пересоздаёт ring, а только обновляет config, system и instance.
5.4 Sender task
Параметры: стек LOG_NET_TASK_STACK (6144 для HTTP без TLS), приоритет tskIDLE_PRIORITY + 1, ядро tskNO_AFFINITY (настраивается). Chunk-буфер размером LOG_NET_CHUNK_SIZE (4096) выделяется один раз при старте, не на стеке.
Цикл:
1. Ждать ulTaskNotifyTake с таймаутом LOG_NET_FLUSH_INTERVAL_MS (2000).
2. Если логирование выключено: очистить ring и pending, вернуться к ожиданию. Если конфиг невалиден или сеть не готова (FR-11): ничего не отправлять, записи остаются в ring.
3. Если pending пуст: собрать пачку. Вычитывать элементы ring (xRingbufferReceive с timeout 0, копирование в chunk, сразу vRingbufferReturnItem), пока в chunk остаётся не меньше LOG_NET_LINE_MAX + 64 байт (запас под маркер потерь). Присвоить пачке seq.
4. Если накопились потери, добавить в начало пачки строку вида [netlog] dropped N records и обнулить счётчик. Маркер становится частью pending, поэтому при ретрае пачка уходит идентичной.
5. Пустую пачку не отправлять.
6. Отправить (§5.5). Успех: любой код 2xx, pending очищается, backoff сбрасывается, seq увеличивается. Неудача: пачка остаётся в pending без изменений (тот же seq), задача спит backoff (1 с, удвоение до 60 с). Пока ретрай не удался, ring продолжает копить, потери считаются.
7. Если после успеха в ring остались данные, собирать следующую пачку без ожидания, но с vTaskDelay(1) между пачками, чтобы не голодали другие задачи.
Сообщения об ошибках отправки пишутся в консоль из sender-задачи (в сеть они не попадают, см. §5.2) и ограничиваются по частоте: не чаще раза в 10 секунд.
5.5 HTTP-протокол
• POST http://host:port/uri, Content-Type: text/plain. Тело: пачка строк, разделённых LF, передаётся как указатель и длина (POST(uint8_t*, size_t)).
• Существующие заголовки: X-SYSTEM, X-INSTANCE.
• Новые заголовки:
    ◦ X-BOOT-ID: случайное 32-битное значение в hex, генерируется один раз за загрузку.
    ◦ X-SEQ: номер пачки в рамках загрузки, при ретрае тот же.
    ◦ X-UPTIME-MS: esp_timer_get_time() / 1000 на момент отправки.
    ◦ X-EPOCH-MS: только если время синхронизировано (time(nullptr) больше 1700000000).
    ◦ X-DROPPED-TOTAL: накопленное число потерянных записей с момента загрузки.
• HTTPClient: один экземпляр в sender-задаче, setReuse(true), setConnectTimeout(LOG_NET_CONNECT_TIMEOUT_MS), setTimeout(LOG_NET_TIMEOUT_MS). При ошибке соединения вызвать end() и переподключиться на следующей попытке. При смене конфигурации соединение закрывается.
• Время строк: в строке остаётся время от старта ([%6u] Arduino или (ms) IDF), приёмник пересчитывает по формуле t_строки = X-EPOCH-MS - (X-UPTIME-MS - uptime_строки). Формулу описать в README. Если X-EPOCH-MS отсутствует, приёмник использует своё время получения.

6. Функциональные требования
• FR-1. Хук не аллоцирует память, не берёт mutex, не блокируется (§5.2).
• FR-2. Ring buffer выделяется один раз и не растёт.
• FR-3. При переполнении отбрасывается новая запись, счётчик dropped увеличивается атомарно.
• FR-4. В ring пишется только при включённом логгере. При выключении ring и pending очищаются.
• FR-5. Вывод в консоль идёт через прежний vprintf-хук, а не через ets_printf.
• FR-6. Нормализация записи: ANSI, CRLF, усечение с маркером.
• FR-7. Записи, порождённые sender-задачей, в сеть не попадают.
• FR-8. Вся сетевая работа выполняется в sender-задаче. loop() и прикладные задачи не блокируются ни при каком состоянии сети.
• FR-9. Тело запроса передаётся с явной длиной.
• FR-10. Успех: любой 2xx. Неудача: ретрай той же пачки с тем же X-SEQ и экспоненциальным backoff.
• FR-11. Готовность сети определяется по умолчанию как WiFi.isConnected() или (если доступен ETH.h) ETH.connected(). Переопределяется через setNetworkReadyCheck(std::function<bool()>). Пока сеть не готова, отправка не выполняется.
• FR-12. Фильтр уровня для сети (LOG_NET_MIN_LEVEL). Уровень определяется по шаблону [E], [W], [I], [D], [V] (формат Arduino) или E (, W ( и т.д. (формат IDF). Неопознанная строка считается INFO. Консольный вывод не фильтруется.
• FR-13. Хук и ресурсы создаются в init(). Конструктор глобального объекта тривиален (глобальные конструкторы выполняются до старта планировщика). Повторный init() безопасен.
• FR-14. init() всегда сохраняет system, instance и конфиг. Валидность конфига вычисляется отдельно (isConfigured()). Отправка идёт только при configured && enabled.
• FR-15. getStats() возвращает: произведено записей, потеряно, отправлено пачек, неудачных пачек, отправлено байт, последний HTTP-код, свободное место в ring.
• FR-16. Макросы LOGx фильтруются на этапе компиляции по уровню (CORE_DEBUG_LEVEL), раскрываются в do { ... } while (0). Идентификаторы __log_* переименовать в EDLOG_*. LOG_BUFFER_SIZE либо удалить, либо взять в скобки.
• FR-17. Настройки применяются атомарно: единый метод applySettings(config) и applySettings(config, enabled), внутри один захват mutex.
7. Нефункциональные требования
• Память: статически около 24 КБ (ring) + 4 КБ (chunk) + 6 КБ (стек). После init() heap не растёт: изменение heap_caps_get_free_size(MALLOC_CAP_8BIT) не более 512 байт за час стресс-теста.
• CPU: вклад сетевой части хука (без консольного вывода) не более 100 мкс на запись в 100 байт при 240 МГц (целевой показатель, измерить через esp_timer_get_time).
• Mutex настроек берётся только sender-задачей, сеттерами и геттерами. Внутри него ничего не логируется.
• Без delay() и busy-wait в прикладном контексте, критические секции не длиннее нескольких микросекунд.
• Сборка без warnings при -Wall -Wextra.
• README с описанием архитектуры, всех define и формата запроса.
8. Изменения в LogSettingsHandler
• Вместо последовательных setConfig, enable и чтения isEnabled использовать единый applySettings. onApplied получает итоговое состояние из логгера, а не из JSON.
• Дополнительная валидация: uri должен начинаться с /, host не содержит пробелов и ://. Ошибки: 422 с message в существующем стиле (invalid uri, invalid host).
• После успешного применения sender закрывает keep-alive соединение и подхватывает новую цель.
• Необязательно (P2): GET /api/log/stats, JSON со статистикой из FR-15.
• Остальное поведение (коды ответов, лимит 1024 байта, формат JSON, логика onApplied) не менять.
9. Структура файлов
• log_config.h: без изменений.
• log_options.h: все compile-time define.
• log_format.h (и .cpp при необходимости): чистые функции без зависимостей от ESP (нормализация строки, определение уровня, сборка маркера потерь). Нужны для unit-тестов на хосте.
• log.h: только публичный API, макросы и LogStats. Без HTTPClient.h, без static-функций.
• log.cpp: хук, ring, sender, HTTP.
• log_handlers.hpp: по §8.
• README.md.
• tools/mock_receiver.py и сценарии стресс-теста.
10. Тестирование и приёмка
Unit-тесты (на хосте, если проект на PlatformIO, иначе простой тестовый бинарь): нормализация (ANSI, CRLF, усечение, пустая строка), определение уровня (Arduino, IDF, неизвестный формат), сборка маркера потерь.
Mock-приёмник: HTTP-сервер, проверяет X-SEQ (пропуски, повторы), считает строки, умеет отвечать 204, 200, 500, зависать и отключаться.
Сценарии на железе (Wi-Fi плата и плата с Ethernet):
1. Базовый. 4 задачи, суммарно 100 записей/с по ~100 байт, 30 минут, приёмник отвечает 204. Ожидание: 0 потерь, порядок записей внутри задачи сохранён.
2. Всплеск. 1000 записей за 100 мс. Потери допустимы, но сумма принятых строк и значений в маркерах dropped в точности равна числу сгенерированных.
3. Приёмник недоступен 5 минут при 10 записях/с. loop() не блокируется (добавка к длительности итерации не более 5 мс), память не растёт. После восстановления приходит сохранённая часть, затем маркер потерь, затем поток без разрывов.
4. Приёмник отвечает 500, затем 204. Ретрай шлёт ту же пачку с тем же X-SEQ, на приёмнике после дедупликации по X-BOOT-ID и X-SEQ дублей нет.
5. Включение и выключение через /api/log/settings: при enabled=false heap и ring не растут, смена host и port применяется без перезагрузки.
6. Нет сети или Ethernet-линка, затем появление. Sender не шлёт и не падает, после появления сети начинает отправку.
7. Отсутствие петли. При приёмнике, возвращающем 500, трафик не нарастает лавинообразно, в тело пачек не попадают сообщения об ошибках отправки.
8. Стек. У sender-задачи запас uxTaskGetStackHighWaterMark не менее 1 КБ. Расход стека хуком на самой маленькой прикладной задаче в пределах цели §5.2.
9. Heap. Сценарий 1 в течение часа: изменение free heap не более 512 байт, min free heap не падает.
Критерии приёмки: все сценарии пройдены, сборка без warnings, сигнатуры публичного API не изменены, приложен отчёт с измерениями (стек, время хука, heap, статистика).
11. Вне объёма
Авторизация эндпоинта настроек, TLS, изменения приёмника и конфигурации Loki, хранение хвоста лога в RTC-памяти для post-mortem после краша, PSRAM, другие транспорты (UDP syslog, MQTT), персистентность настроек (остаётся за onApplied).
12. Допущения и вопросы заказчику
• Среда сборки (PlatformIO или Arduino IDE), версии Arduino-ESP32 (2.x на IDF 4.4 или 3.x на IDF 5.x) и ArduinoJson. По умолчанию сохраняется совместимость с текущими.
• Приёмник нормально принимает дополнительные заголовки X-*.
• Логи отправляются только при enabled=true, захват логов до включения (ранний boot) не требуется.
• networkLogger живёт всё время работы прошивки, остановка sender-задачи не требуется.
